# MG400 视觉找物项目

## 项目目标

本项目使用 Dobot MG400 四轴机械臂和 Intel RealSense D435 深度相机，实现通过自然语言寻找物体的任务。

当前阶段暂时使用终端文本代替语音输入。规划中的完整流程如下：

1. 启动硬件并使能；如果未在 Home，则先低速归位，获取稳定的新图像后开放输入。
2. 用户在终端输入需要寻找的物体，例如“找到红色杯子”。
3. 视觉大模型根据 D435 彩色图像定位目标物体。
4. 使用对齐后的深度图和相机内参计算目标三维坐标。
5. 将目标坐标从相机光学坐标系转换到 `mg400_origin_link`。
6. 机械臂移动，使法兰中心到达目标表面正上方 5 cm。
7. 终端显示任务完成信息。
8. 机械臂抬升并返回 Home，确认到位并获取新图像后等待下一次输入。

未来接入语音模块时，只替换输入和播报模块，视觉定位、坐标转换和运动控制流程保持不变。

## 已确认的需求

- 相机固定在不随物理 J4 旋转的腕部外壳上。
- 相机 TF 的父坐标系应为 `mg400_link5`。
- MG400 法兰安装面在运动过程中始终垂直向下。
- J4 只控制法兰绕竖直轴的旋转，当前任务不要求固定 yaw。
- 任务目标是让法兰中心到达目标可见表面正上方 0.05 m。
- 检测失败、深度无效或目标不安全时，不发送运动命令。
- 运动过程中发生故障后，不自动发送返回指令。
- 第一版只考虑简单、静态、单目标环境。
- 多个同类物体的选择规则暂时只预留接口。
- 千问使用统一视觉接口，当前配置为 qwen3-vl-plus，后续可替换型号。

## 当前已有内容

- MG400 ROS 2 驱动、消息、运动 Action 和相关启动文件。
- RealSense ROS 2 驱动。
- PlayStation 手柄相关驱动。
- `easy_handeye2` 标定工具。
- 自定义 `chessboard_detector` 棋盘检测节点。
- 一个手工填写的 `mg400_link5 -> camera_link` 静态 TF。
- `object_finder` 上层任务包初版，包括终端/话题输入、状态输出、视觉
  接口、RGB-D 同步、深度定位、TF 转换、观察位核验、安全联锁和运动
  状态机。

当前现场配置已按用户确认启用真机运动，速度/加速度为 5%。
Home 使用 `mg400_origin_link` 中的法兰 `[x,y,z,yaw]`（米/弧度）：

```yaml
home.mode: pose
home.pose: [0.350, 0.000, 0.150, 0.000]
```

对应 MG400 RViz 面板 `x350 y0 z150 r0`。启动时会自动归位，归位/任务期间
暂停输入，成功返回后开放下一次输入；运动失败时不自动返回并暂停输入。
使用方法、完整参数及测试见 [object_finder 使用说明](src/object_finder/README.md)。
准确相机外参、完整碰撞路径和整机可靠性仍需要现场验证。

## 尚未解决的问题

### 1. 相机外参尚未准确标定

当前静态变换为：

```text
translation: (0.04, 0.0, -0.02) m
rotation:    roll = 0, pitch = pi/2, yaw = pi
parent:      mg400_link5
child:       camera_link
```

其中平移来自手工测量，旋转方向可能错误。这组参数只能用于临时调试，不能直接用于真机自动运动。

需要完成：

- 测量或标定 `mg400_link5 -> camera_link` 的完整三维平移和旋转。
- 使用四元数保存旋转，避免欧拉角顺序产生歧义。
- 在机械臂工作空间内选择多个已知测试点，验证相机坐标转换后的实际误差。
- 确认 TF 树中存在连续链路：

```text
mg400_origin_link
  -> ...
  -> mg400_link5
  -> camera_link
  -> camera_color_optical_frame
```

MG400 的末端缺少 roll、pitch 运动，传统六自由度手眼标定可能缺少足够的旋转激励。因此不能只依据“标定算法成功”判断结果可用，必须进行实物点位验证。

### 2. 棋盘检测坐标系配置已修复，尚待实机验证

`solvePnP` 根据彩色图像和相机内参得到的结果属于 `camera_color_optical_frame`，但当前启动文件把 `camera_frame` 覆盖成了 `camera_link`。

代码已将其恢复为 `camera_color_optical_frame`。实机时仍需检查彩色图、
`CameraInfo` 和 TF 的帧名与时间戳，并用已知点验证轴方向。

### 3. 静态 TF 启动文件已安装，但参数仍是临时值

`src/chessboard_detector/setup.py` 已安装目录中的全部 launch 文件，因此构建后
可以启动：

```bash
ros2 launch chessboard_detector tf.launch.py
```

位置、旋转和父子帧也已暴露为 launch 参数；但是默认外参仍是手工测量值，
完成标定与点位验证前不得据此启用自动运动。

### 4. 观察位置和返回位置已指定，还需现场覆盖/路径验证

观察与返回使用同一个 Home，已指定为基座系法兰
`[0.350, 0.000, 0.150, 0.000]`（米/弧度）。程序检查实时 TF；
启动不在位时发送 MovJ 归位，成功返回后重新取图再开放输入。

观察位置需要同时满足：

- D435 能覆盖预期工作区域。
- 目标深度处于相机有效测距范围内。
- 相机和支架不会与机械臂、桌面或物体碰撞。
- 机械臂能够从该位置安全到达目标上方。

### 5. 5 cm 间隙已由用户确认，完整路径仍需验证

任务要求法兰中心位于物体表面上方 5 cm，但相机安装在腕部外壳上，支架或相机可能低于法兰参考点。

用户已确认急停可用，目标上方 5 cm 时相机、法兰和线缆不会碰撞。
为了可重复验收，仍建议记录：

- 相机和支架最低点相对法兰中心的高度。
- 桌面在 `mg400_origin_link` 中的高度。
- 目标物体允许的最大高度。
- 法兰、相机和支架所需的最小安全间隙。

如果相机或支架可能先接触物体，必须增加最终悬停高度，不能固定使用 5 cm。

### 6. RGB 与深度同步定位已实现初版，但尚未实机验证

`object_finder` 已使用近似时间同步接收彩色图、对齐深度图和
`CameraInfo`，并在目标中心区域过滤无效深度、检查最少样本数、计算
三维中值点。目标掩码存在时，有效深度比例只在掩码内部计算。
实机运行时仍需要启用并验证：

- `enable_sync:=true`
- `align_depth.enable:=true`
- `/camera/camera/color/image_raw`
- `/camera/camera/aligned_depth_to_color/image_raw`
- `/camera/camera/color/camera_info`

当前固定框测试接口可以验证该链路；目标掩码接口已经预留，但要等千问
适配器确定后才能验证真实物体边界与深度取样效果。

### 7. 千问视觉接口已接入，仍需统计现场可靠性

当前配置使用千问 `qwen3-vl-plus` 云端 API，密钥来自
`DASHSCOPE_API_KEY` 环境变量。已观察到现场定位输出，仍需验证
不同物体、光照、深度无效和多目标情况下的成功率。

代码中已经预留统一 `VisionGrounder` 接口和 Qwen 配置参数，包括：

- 模型名称。
- 云端或本地服务地址。
- API 密钥读取方式，密钥不得写入仓库。
- 请求超时和重试次数。
- 文本和图像输入。
- 目标框或目标掩码。
- 类别、置信度和候选目标列表。
- 未找到、多个目标、服务失败等状态。

大模型只负责理解目标和二维定位，不允许直接生成并执行机械臂坐标。三维计算、TF 转换和安全判断必须由确定性程序完成。

### 8. 多目标接口已预留，最终选择规则尚未确定

当前代码采用保守策略：

- 只有一个高置信度目标时继续执行。
- 没有目标时保持不动。
- 出现多个同类目标时提示用户进一步说明，不自动选择。

以后可增加“最近、最大、最左、指定颜色”等策略，但应通过独立策略接口实现。

### 9. 基础运动顺序已实现，但尚未通过真机验证

不应直接使用一次 `MovJ` 从观察位运动到目标表面上方 5 cm，因为关节插补路径不能保证法兰、相机和支架始终远离桌面。

`object_finder` 已按以下顺序组织 Action：

```text
观察位拍照
  -> 目标上方安全接近点（MovJ）
  -> 垂直下降到目标表面上方 5 cm（MovL）
  -> 垂直抬升到安全高度（MovL）
  -> 返回观察位置（MovJ）
```

现场 YAML 已打开运动及 Home、工作空间和物理间隙联锁。
接近高度为物体表面上方 0.15 m，终点为上方 0.05 m，速度/加速度 5%。
工作区暂定 `[0.25,0.36,-0.10,0.10,-0.11,0.20]`（米）。
只检查端点不能保证整条路径无碰撞，启动归位路径同样需现场确认。

### 10. 驱动取消运动不会真正停止机械臂

当前 MG400 ROS 2 驱动接受 Action cancel 请求，但代码中没有实现停止正在执行的 `MovJ`。此外，运动 Action 使用固定 10 秒超时，超时并不等价于机械臂已经停止。

在真机自动执行前，需要明确并验证：

- 正常任务取消时使用的停止命令。
- 通信断开时的处理方式。
- Action 超时后如何确认机械臂真实状态。
- 控制器报警时是否允许继续发送命令。
- 急停只用于危险情况，不能作为普通流程控制手段。

### 11. 上层失败状态机已实现，但可靠停止仍需底层支持

当前状态机在检测、深度、TF、安全检查或 Action 失败后不再发送后续
运动指令，但这只能保证上层停止下发命令，不能保证已经在执行的运动
立刻停止。

任务状态机至少需要区分：

- 检测失败：仍在观察位，不运动。
- 坐标或安全检查失败：不运动。
- Action 被拒绝：不发送后续命令。
- 运动中报警或超时：请求可靠停止并等待人工处理。
- 返回初始位失败：不继续自动恢复。

## MG400 官方运动范围

越疆官方参数给出的最大工作半径为 440 mm，J1 为 ±160°、J2 为
-25°～85°、J3 为 -25°～105°。J4 在当前官方产品页、旧版硬件手册和
本仓库 ROS 2 驱动中的限制不一致，因此代码没有放宽驱动限制，而是采用
驱动的 ±160° 并保留 1.05° 安全边界。

`object_finder` 已增加 0.440 m 水平半径硬限制。该限制只代表机械规格
上限，不能代替根据桌面、相机支架和障碍物设置的
`safety.workspace_bounds`。

## 建议实施顺序

1. 棋盘检测光学坐标系配置和启动文件安装已完成代码修复。
2. 完成并验证 `mg400_link5 -> camera_link` 外参。
3. 启用彩色与对齐深度同步，完成二维像素到三维点的离线测试。
4. 使用已知测试点验证相机坐标到机械臂坐标的误差。
5. 终端/话题输入、启动 Home 门控和固定框 dry-run 接口已实现。
6. 千问适配和单目标定位已接入，继续测试现场准确性。
7. 任务状态机、拍照时刻 TF、安全检查和终端状态输出已实现初版。
8. 在低速度、空载、有人监护且急停可用的条件下测试单段运动。
9. 验证安全接近、垂直下降、抬升和返回的完整流程。
10. 坐标精度和异常处理通过验收后，再启用自动任务。

## 真机运行前的最低验收条件

- 完整 TF 树连续且无重复发布者。
- 多个已知点的坐标转换误差满足任务要求。
- 目标深度无效时机械臂不会运动。
- 多目标或低置信度时机械臂不会运动。
- 目标位姿超出工作空间时机械臂不会运动。
- 已验证最终 5 cm 高度不会导致相机、支架或法兰碰撞。
- 已验证运动超时、控制器报警和通信断开的处理方式。
- 操作人员能够随时使用实体急停。
